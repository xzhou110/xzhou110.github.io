# Employer Portfolio Refresh

## Request and Chosen Direction

The owner asked to catch up on the portfolio and other apps, polish the look, add suitable projects, and update the framing to support connections with future employers. After comparing the existing layout, an editorial showcase, and a minimal gallery, the owner selected **A · Editorial Showcase (Recommended)**.

The goal is to help a hiring reader understand Lukas's work, inspect a meaningful product or engineering decision, and start a conversation. The positioning remains AI, Data Science & Product; technology lists are evidence about a project rather than a claim of independent mastery of every library.

## Selection and Framing

- Lead with XuSeak To-Do for mobile product delivery, Car TCO Compare for data-driven decisions, and Multi-Agent Build Orchestrator for AI workflow design.
- Add Dream Laws for reproducible game systems, Local App Kit for shared engineering foundations, and Creator Advisors for source-constrained AI synthesis. With XuSeak To-Do, these bring the selection from seven to eleven.
- Retain the original web comparison apps and local-tool cases, with more concise descriptions. Every card exposes its current release state and one consequential decision before the reader opens the evidence.
- Keep earlier public data-science and AI experiments in the existing archive. All eight archive repository destinations were verified public during the refresh.
- Exclude a third-party website launcher, paused collection tooling, and a native alarm concept awaiting signed-device acceptance from the main selection. Breadth should add evidence of authorship and working behavior.
- Remove old test-count, operating-cost, and service-health claims that cannot be treated as current. Project evidence was reviewed on October 27; historical tests were inspected as evidence, not rerun as part of this website change.

## Reproduction Brief

> Refresh this portfolio for a future employer evaluating work across AI, data science, and product. Read the personal projects' own maps and relevant evidence before writing. Preserve the distinction between public releases, TestFlight, local tools, and prototypes. Select complementary projects. Put a short outcome and one meaningful decision on each card; keep the problem, implementation, verification, and limitations in an accessible disclosure. Use the chosen editorial visual direction: a deep green introduction, three suggested starting points, a leading mobile case study, then a compact two-column gallery. Preserve categories, direct links, keyboard navigation, both themes, and all existing support URLs. Use only reviewed public screenshots or explicitly labelled illustrations. Apply the existing publication gate to every public source and generated file.

The source of the result is `content/portfolio.json`, `render.mjs`, and `assets/site.css`; the selected project order and starting links are content, not hidden rendering rules. The product and game previews are semantic HTML/CSS illustrations with fictional sample tasks. No external artwork, fonts, analytics, or runtime dependencies were added.

## Quality Bar

1. A first-time reader can identify the focus, open a relevant case, see an actual decision, and find contact without instructions.
2. Claims distinguish implementation from acceptance and release. AI assistance is disclosed with concrete examples of checks finding defects.
3. Public links resolve to the intended project. Private source, account data, personal notes, and unlisted test builds remain outside the artifact.
4. Narrow screens do not scroll sideways; themes stay readable; keyboard selection retains focus until Go; filters, direct links, Back, and reload keep their behavior.
5. The full candidate and exact staged bytes pass the existing publication gate. Existing reviewed image bytes stay unchanged.
6. After publication, Pages must report the pushed commit and the deployed HTML/CSS/JavaScript must match the approved local output.
