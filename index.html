01

XuSeak To-Do

TestFlight · App Review in Progress

An iPhone app that brings today’s work, to-dos, habits, ideas, and a calendar into one calm daily workflow.

  • Offline First
  • Optional Sync
  • Home Screen Widget

A Key DecisionMake the app useful offline; add account sync without making it a prerequisite.

iPhone App · Private Source

Read Case Study: XuSeak To-Do
Problem
Tasks, recurring habits, and ideas belong to the same day, but often live in separate tools. A useful daily app needs to make the next action clear without requiring account setup first.
What I Built
An offline-first iPhone app with Today, To-Do, Habits, Ideas, and Calendar, optional account sync, and an interactive Home Screen widget. The work includes product design, data modeling, native interaction refinement, and release preparation.
How It Works
A pure TypeScript engine sits behind a React Native interface. Local persistence works independently of the account layer; sync merges changes through a separate adapter. I direct product and design decisions, review AI-assisted implementation, and test the installed experience.
Where It Stands
Installed through TestFlight and submitted for App Review. Review follow-up is in progress; there is no public App Store release to download yet.
Evidence and Limits
  • Independent review caught second-device default preferences blocking sync and stale writes replacing newer changes. Per-key merging and regression tests now cover those cases.
  • Automated checks are separate from physical-device acceptance. Two-device sync and account-deletion acceptance remain open.
  • The preview uses fictional tasks. No account data, personal task list, or private source is included.

02

Car TCO Compare

Live Web App

Compare the estimated cost of owning up to six cars, with assumptions you can change and a breakdown you can inspect.

  • Editable Cost Model
  • Real Listings
  • Email Backend

A Key DecisionMake the assumptions editable so the ranking can be challenged.

Open App  ↗View Source ↗
Read Case Study: Car TCO Compare
Problem
Sticker price and monthly payments leave out much of the cost of owning a car. I wanted to compare different vehicles under the same holding period, mileage, and financing assumptions, and inspect what changes the ranking.
What I Built
A car-ownership calculator with a seven-part cost model, side-by-side comparisons, cumulative cost charts, and a snapshot of real listings. A separate email-alert prototype ranks listings by estimated ownership cost.
How It Works
The pure TypeScript calculation engine is separate from the React interface and reused in Car Shopping. Listing snapshots keep the comparator static. Supabase, Resend, and scheduled GitHub Actions support the email-alert prototype with double opt-in.
Where It Stands
The comparator is publicly available. The alert backend is a proof of concept; a commercial subscription service has not launched. This project demonstrates a complete path from a model to an interactive product and a supporting backend.
Evidence and Limits
  • Cost assumptions are illustrative segment-level estimates, not predictions of an individual buyer’s expenses. Listings are snapshots, not guaranteed current inventory.
  • Engine tests cover calculations, depreciation, and vehicle resolution. The model documentation makes the assumptions inspectable.
  • The alerts prototype has a public review record. Historical checks are not a promise of current service reliability.

React · TypeScript · Vite · Vitest · Supabase · Resend · GitHub Actions · GitHub Pages

What I Built

Dream Laws: Card Roguelike

TestFlight · In Development

A mobile deckbuilder where each dream changes the rules of play, backed by a reproducible game engine and balance simulations.

  • Seeded Engine
  • Simulation Tools
  • Save Migration

A Key DecisionUse simulation to verify the rules; use playtesting to judge the experience.

Mobile Game · Private Source

Read Case Study: Dream Laws: Card Roguelike
Problem
A card game needs varied choices that remain understandable. Changing the rules adds variety, but makes progression, difficulty, and saved-state behavior harder to reason about.
What I Built
A portrait card roguelike with encounters, deck-building decisions, branching progression, and persistent runs. Simulation tools exercise the game engine across repeatable seeds.
How It Works
A pure seeded engine separates game rules from the mobile interface. Replays and generated-map checks expose progression errors. Save migrations preserve ongoing runs as the rules change.
Where It Stands

  • Dated verification records include exact replays and generated-map checks. Repeatability and valid routes do not establish enjoyable difficulty.
  • The public case study does not expose private source or link to the separate unlisted tester build.

Local App Kit

Public Package · v0.1.0

A shared TypeScript runtime for local apps: safe file writes, localhost request guards, live updates, and service recovery.

  • Zero Runtime Dependencies
  • Conflict Detection
  • Real-Socket Tests

A Key DecisionExtract repeated infrastructure only after multiple apps need it.

Developer Library

View Source ↗
Read Case Study: Local App Kit
Problem
Several local apps needed the same file safety, request validation, and recovery behavior. Maintaining separate copies made a fix easy to miss in one consumer.
What I Built
A small, versioned library for atomic JSON writes with ETags, a guarded static server, server-sent events, and single-server locking, with no runtime dependencies.
How It Works
Shared mechanisms sit behind explicit interfaces while each app keeps its own domain logic. Real-socket parity tests check that extracting the shared implementation preserves consumer behavior.
Where It Stands
Version 0.1.0 is released and used by AI Usage Tracker. Other planned consumers have not yet migrated; this is an incremental extraction.
Evidence and Limits
  • Parity tests check consumer behavior through actual HTTP sockets.
  • One application has migrated. The package is not presented as a completed migration of every local app.
  • Localhost guards and conflict checks address specific risks; they are not a claim of absolute security.

  • Transcript Matching
  • Computed Timestamps
  • Local Reader

Local Knowledge App · Private Source

Read Case Study: Creator Advisors
Problem
Useful ideas are scattered across long videos. Summaries are easier to skim, but can lose context or point to a timestamp that does not support the claim.
What I Built
A transcript-to-knowledge pipeline with source-linked topic pages and a desktop and browser reader. Transcription adapters feed one pipeline, and quotation matching produces the citation locations.

AI assists organization and synthesis. Deterministic import checks require quoted wording to match the transcript and compute timestamps from those matches. The reader keeps sources accessible beside the interpretation.

Car Shopping

Live Web App

A used-car shortlist that raises risk flags, tracks features honestly, and ranks candidates by estimated cost of ownership instead of sticker price.

  • Risk Flags
  • Cost Ranking
  • Google Sheets Sync

A Key DecisionTreat an unknown vehicle feature as unknown, not as absent.

Open App  ↗View Source ↗
Read Case Study: Car Shopping
Problem
Shopping for a used hybrid SUV with a deadline, I had listings scattered across five sites with inconsistent wording. Sticker price is a poor way to rank near-identical cars: the cheaper one can depreciate faster, carry rental-fleet mileage, or hide an accident.
What I Built
A used-car shortlist with feature tracking, risk flags, estimated ownership costs, comparison, and Google Sheets export. Listings are captured with an assistant into a typed seed catalog; the app does not scrape listing sites.
How It Works
A pure domain engine handles the risk rules, ranking, and export. The ownership-cost engine is reused from Car TCO Compare. Browser storage holds the working shortlist, and an Apps Script endpoint supports Sheets export.
Where It Stands
Built for my own car search and available as a public, single-user web app. It shows how a broad cost model can become a focused decision workflow.
Evidence and Limits
  • Review found an unused URL-import feature could replace saved work. I removed it; regression tests verify that crafted URLs cannot change saved data.
  • The public decision record explains the architecture and trade-offs.
  • Cost figures are estimates. Risk flags surface information to investigate; they do not verify a vehicle’s history.

  • Windows Sidebar
  • Quota Windows
  • Explicit Freshness

A Key DecisionKeep a missing or stale reading visibly different from available quota.

Local App · Case Study

View Source ↗
Read Case Study: AI Usage Tracker
Problem
Working across AI tools means checking separate usage limits, reset windows, and dashboards. A missing or stale reading can easily look like available capacity unless the interface makes uncertainty explicit.
What I Built
A Windows sidebar and browser dashboard with separate quota windows, reset countdowns, usage history, connection details, and settings. The desktop launcher starts the local service and restores the existing app when opened again.
How It Works
Provider adapters normalize observations into a common model while preserving source timestamps and units. The Windows and browser app is usable, with Codex readings reconciled against their provider source. Claude and Cursor live reconciliation remain pending. Public source is available; account data stays local.
Evidence and Limits
  • Codex has a verified live reading. Claude and Cursor are incomplete integrations, not confirmed live connections.
  • Provider observations retain their timestamps and units. Subscription prices are user-entered and do not establish the size of a quota.
  • The visual is a capability illustration with no account or usage data. The dashboard does not run an AI model.

X Command Center

Private Desktop App

One local hub for project progress, scheduled work, app launch, and the next thing that needs attention.

  • Project Overview
  • Shared Desktop UI
  • Service Recovery

A Key DecisionKeep one shared snapshot behind the desktop and browser views.

Private Local App · Case Study

Read Case Study: X Command Center
Problem
As personal projects grew, the context needed to resume work was scattered across folders, repositories, notes, and schedules. Finding what was unfinished or needed attention became a task of its own.
What I Built
A project hub that connects purpose, status, next steps, app launch, scheduled work, and history. A Windows desktop window and browser use the same local interface and service.
How It Works
A deterministic collector reads an explicit personal-project allowlist and builds one shared snapshot from project documentation, version-control metadata, site checks, and schedules. The interface reads that snapshot. A coordinated local service supports refresh, recovery, and desktop launch; opening the installed app again restores the existing window.
Where It Stands
Available as a local browser and Windows app with Start and Desktop launchers. The design establishes a consistent visual language across related tools while keeping project facts close to their source. The public case study uses a capability illustration instead of a real workspace screenshot.
Evidence and Limits
  • Testing the actual desktop launch action caught an outdated configuration reader that ordinary checks had missed. The callers now share one reader with regression coverage.
  • The collector is deterministic and makes no AI calls. Status comes from project records, not an automatic assessment of productivity.
  • Private project data, schedules, notes, and runtime snapshots are excluded from this case study.

How I Build

I use AI agents to help implement and review. I own the problem framing, product choices, and the decision about what is ready to ship.

01

Start with the Decision

Identify who needs help and what they need to do. Make the assumptions, data limits, and smallest useful workflow explicit.

02

Build for Change

Keep domain rules separate from the interface and services. Write down trade-offs, preserve saved work, and reuse code when real repetition justifies it.

03

Look for What Breaks

Use tests, independent review, and the installed or deployed app. In Car Shopping, review caught an unsafe URL import; I removed it and kept a regression test.
